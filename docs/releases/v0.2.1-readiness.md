## 5. Safe tablet reconnection and deploy prerequisites

The camera's connection and media retrieval are separate physical work. They do
not establish a tablet connection and are not human release evidence. No camera
operation is needed for the tablet checks below.

1. On the tablet, enable **Developer options → Wireless debugging** and read its
   current **IP address & port**. A reboot disables debugging and toggling it changes
   the port. Do not reuse a historical address as evidence of a connection.
2. If this machine is not paired, choose **Pair device with pairing code** on the
   tablet. From the chosen clean checkout run
   `tools/deploy_android.sh pair <IP:PAIRPORT> <6-digit-code>`.
   This pairs only; do not run the normal deploy command yet. The pairing port is
   different from the connection port.
3. Run the SDK's `adb connect <IP:PORT>`, then `adb devices -l`. Use the exact serial
   of the responding device for subsequent reads. Pairing/connection alone does
   not prove which game is installed.
4. Before an authorized install, read the game's package `lastUpdateTime` and
   rescue all played farms using `tools/pull_session.sh`. Device files are in
   `run-as com.daniel.tinyfarm` internal `files/slot1` through `slot3`, not sdcard.
   Verify new play on the recording commit, keep the receipt, and commit the rescued
   evidence. The deploy script performs this check itself and repeats the rescue
   immediately before install; neither pass may be skipped.
5. Use a clean checkout of the settled candidate, excluding only rescued playtests
   from the source-clean check. Prepare `android/build/`, `debug.keystore` and an
   empty `build/` as in [the deploy runbook](../DEPLOY.md). Import with Godot 4.7.2.
   Review generated sidecars before removing any; preserve ignored media and saves.
6. Only after install is authorized, run `tools/deploy_android.sh <IP:PORT>`. It
   stamps the build, regenerates the demo, rescues and verifies play twice, installs,
   launches and saves the non-release build marker. If it refuses a dirty/lost
   recording build or replay mismatch, stop and follow its triage instructions.
   Do not use raw `adb install`, uninstall, clear-data or a manual relaunch to bypass it.

## 6. The human checks on the settled build

**End-to-end play (Daniel).** The existing ruling does not prescribe a new score
or duration. A practical route is: confirm the installed build; open Credits; play
clear → till → plant → water → sleep → harvest → sell; buy and operate a robot;
enter/leave rooms; use the Mark III/workbench and barn features the announcement
promises; save, return to title and Continue the same farm. For later unlocks use
an existing suitable farm or an empty slot, without replacing an occupied farm.
Record problems and the actual route. This route is a checklist for covering the
copy, not a newly imposed acceptance criterion.

**Seven-day robot observation (Daniel, supported by the release owner).** Buy a
Mark III in normal play on the candidate, record the farm/slot, build id, robot,
starting game day and its settings, including rewards, pace, assigned squares,
starting brain and extra practice if present. Watch it work through seven full
in-game days and nights; keep its daily scorecard and a short description of what
it actually did. Record any changes to its settings or interruptions. Say whether
its improvement and behaviour meet the existing plan's words; do not mark a pass
from a plausible chart, an automated demo, or an unobserved week. If it is unclear,
report the observation and ask Daniel for the verdict without changing the gate.

**Preserve the evidence before another launch or deploy.** Backgrounding the game
flushes its session (`main.gd`, `persist_session`). Pull the played slot immediately
with `tools/pull_session.sh --slot <N>`; keep the printed folder, replay, autosave,
trace and verification receipt. Replay on the stamped recording commit with
`godot --headless --path . --script res://tools/verify_replay.gd -- <folder>`.
The pull does not write human conditions: add `session.json` only from Daniel's
actual answers (tester, fresh, prompted, attested_by, attested_on, source), and a
short observation note beside the session with the seven-day record, his verdict
and any screenshots. Several sittings need their own pulled sessions; later play
can overwrite the previous sitting's recording. Never backfill a human pass from
CI or a deployment receipt.

**Record Daniel's release play only after he plays.** Use the two-step button on
[HQ's Sales and Platforms page](http://localhost:8642/#/pillar/sales).
The real service is `GET /api/web-play` for status and `POST /api/web-play` for
recording, with `{"of":"web_play","played":true}`. The legacy name is `web_play`
but the current record means tablet play under S-45. This session only used GET.
HQ records the intended tag, current main commit and date; it cannot observe the
tablet. Confirm HQ's main contains the installed candidate's game content first.
Uncommitted game files block recording; later game-content changes lapse it.
Docs/HQ changes alone do not. The seven-day observation needs its own note; the
button does not record or prove it.
