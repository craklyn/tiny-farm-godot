## 1. Background & Motivation

Can HQ turn a held, reviewed game-code candidate into either a safely landed local-main commit or a truthful, owned next action, without touching Daniel's dirty working checkout? The first live test is the Scenario W weather card. This report records the live cutover, measured checks, failures and follow-up; it does not treat a finished agent session or local green tests as pushed or CI-confirmed code.

- RQ3: Does the queue present a failed review as a held, owned next action rather than an automatic loop or a completed shipment?

## 4. Methodology

The clean integration checkout is `/home/daniel/dev/tiny-farm-godot-main`. HQ code and authoritative local `main` are there; HQ continues to use the existing `/home/daniel/dev/tiny-farm-godot/hq/data` store, and the original checkout remains Daniel's unfinished workspace. The service runs with all three roots explicitly configured. The unattended drain timer and execution policy were left paused during the canary. Each weather attempt used an isolated candidate worktree and the drain's checker and suites; a separate verifier reproduced the held patch at its recorded base and ran the ordinary-speed integration suite with isolated user data.

Evidence pointers below name local files; `hq/data/runs/` is ignored by Git and remains in the live HQ store. Reported counts come from final `Results:` lines and process exit status, not from worker prose.

For RQ2, a run counts as *completed* only when the Godot process ends with one final `Results:` line. Scenario W passes only when its exact dry-at-tap assertion line is present. A completed suite with another failing assertion contributes to the Scenario W count but is not a green full-suite run. The independent ten-run diagnostic used the same four game-file patch on the then-current clean main; the later `verify_held_patch.py` check reconstructed the exact recorded held candidate. Those are different trees, and their evidence is not interchangeable. The qualification script's stop-on-first-red rule was applied as written; its early stop is reported as an incomplete qualification.

Incident A — a private synthetic revision commit invoked the writing-check hook and added `docs/writing_verdicts.json` to the first reviewed candidate. The checker detected it in the diff, so that candidate was invalid as a four-file weather-only patch. The original artifact remains available; the hook and held-patch cleanup paths have since been changed, and any future cleaned candidate needs its own identity and review. Incident B — the second worker interpreted delayed command results as timeouts. The JSONL stream and checker establish one full-green and one completed-red run; its prose is not used as the count. Incident C — the candidate-bound verifier stopped after a completed red suite whose Scenario W assertion had passed. That is a correct failure of the *full-suite* qualification but incomplete weather-flake measurement; an opt-in continue-and-record mode is being tested without converting red runs to green.

Incident D — in the third supervised trial, the fresh worker checkout lacked Godot's imported class cache. Its first integration loop produced parse errors and stalled without a result. The test subprocess alone was stopped after its exact process group was identified; the worker then ran `godot --import` and continued. The parse-error loop is invalid verification data, not a weather failure. The system should perform this preflight before asking a coding agent to count long runs.

Incident E — the third worker saved ten separate green full-suite logs, but nine were produced inside one shell command. The bounded JSONL evidence reader treats that grouped command as one tool result, so the review could not substantiate ten separate completions from its input. This is an evidence-handoff limitation, not proof that those saved runs failed. The checker held the candidate; the external candidate-bound verifier is being used to record each run separately with hashes and process status.

Incident F — the per-card autonomy guard compared recorded dollar cost with a dollar cap, but the Codex adapter currently records these model calls as unpriced. That leaves the cost guard effectively open for this provider even when the session uses millions of tokens. The weather card's first three supervised worker/checker attempts used 1,613,031, 713,027 and 2,550,932 total model tokens respectively, 4,876,990 combined; 4,526,336 of those were cache-read input tokens. These are model-throughput counts, not an asserted conversion to Daniel's weekly usage percentage. A token-denominated cap and a no-worker re-review path are required before broad autonomy.

Incident G — the first evidence-only re-review accepted the unchanged candidate, and its candidate suites passed, but the fresh prospective integration checkout had never run `godot --import`. Missing global-class cache entries produced parse errors for `SimRng` and `SimWorld`; the integration process slept until its exact subprocess was stopped. The gate held the patch, correctly, and recorded no local-main commit. The prospective checkout now receives the same import preflight as worker and reviewer checkouts. A later zero-model gate retry passed unit tests but hit a completed Mark III placement failure in Scenario AO. This is a genuine red full suite, even though Scenario W's separate ten-run qualification was green. Five fresh unmodified-main baselines were subsequently green; that makes a candidate-specific interaction plausible but does not prove causation because the seed and timing were not held constant.

## 6. Conclusions & Selection Logic

The queue respected the most important safety boundary: review and prospective-suite failures left local main and Daniel's overlapping game files unchanged. This is a measured safety success, not a shipping success. The exact weather candidate passed its ten-run Scenario W qualification, but a later full-suite Mark III failure blocked landing. The five green baselines narrow the diagnosis without settling it. Keep the timer paused; use candidate-bound repeated-test evidence and a matched-seed investigation before another landing attempt. The new per-card token cap prevents an unpriced model provider from silently repeating costly worker sessions.

Local `main` is ahead of `origin/main`; no remote push or matching remote CI run is part of this activation. A local landing must remain distinct from CI confirmation. The service can be used read-only during the pause; do not interpret a stopped timer as active bullpen work. The next release milestone for broad HQ architecture remains after the v0.2.1 Mark III tag, contingent on measured flow rather than another speculative rewrite.
